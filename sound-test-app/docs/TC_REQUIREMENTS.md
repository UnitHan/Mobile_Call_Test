## 1. 개요

### 목적
ixi-O(익시오) 앱의 통화 품질을 iOS↔Android 실기기 환경에서 자동으로 검증한다.  
세 가지 TC가 독립적으로, 또는 순차적으로 실행되며 결과는 대시보드에 통합 표시된다.

### 시스템 구성
```
┌──────────────────────────────────────────────────────┐
│  Tauri 대시보드 (macOS)                               │
│  ├─ TC 선택 / 실행 / 중단                             │
│  ├─ 실시간 진행 상태 스트리밍                          │
│  └─ 결과 보고서 통합 뷰                               │
├──────────────────────────────────────────────────────┤
│  Python 테스트 엔진 (Appium + 음원 재생)               │
│  ├─ tc01_runner.py  (일반 통화 + 자동 음단절 분석)    │
│  ├─ tc02_runner.py  (보이스피싱 감지 + 자동 음단절)    │
│  └─ tc03_runner.py  (MOS 측정 전용)                   │
├──────────────────────────────────────────────────────┤
│  실기기                                               │
│  ├─ iPhone (iOS ixi-O)                               │
│  └─ Galaxy (Android ixi-O)                           │
└──────────────────────────────────────────────────────┘
```

## 2. TC 상세 정의

### 2.1 TC_01 — 일반 통화 테스트

| 항목 | 내용 |
|------|------|
| **목적** | 정상 통화 환경에서 iOS↔Android 양방향 음원 재생이 끊김 없이 완료되는지 검증 |
| **사용 음원** | 설정에서 첨부한 **일반 통화 음원** (TC_01 할당 파일) |
| **PASS 조건** | 음원 재생 완료 후 통화 정상 종료 |
| **FAIL 조건** | 음원 재생 중 통화 단절 / 앱 크래시 / 타임아웃 |
| **별도 구현 필요** | ✅ Phase 2 (AOS 발신 → iOS 수신) |

#### 실행 시퀀스

```
Phase 1: iOS 발신 → Android 수신  (기존 스크립트 재사용 가능)
─────────────────────────────────────────────────────────
① iOS ixi-O 앱에서 Android 번호로 발신
② Android ixi-O 앱에서 자동 수신
③ 음원 재생 시작 (화자1: 일반 음원)
④ 음원 재생 완료 → 통화 종료
⑤ 결과 수집 (MOS, 스크린샷 발신/수신 양방향)

Phase 2: Android 발신 → iOS 수신  ← 신규 개발 필요
─────────────────────────────────────────────────────────
① Android ixi-O 앱에서 iOS 번호로 발신
② iOS ixi-O 앱에서 수락 (WDA 또는 CallKit 후킹)
③ [중요] iOS 수신 수락 감지 즉시 → 백그라운드 스레드로
   00:00 타이밍에 음원 재생 시작
   - 수락 감지 방법: WDA로 통화 화면 진입 감지 또는
     Appium element 상태 폴링 (통화 타이머 00:00 등장)
   - 재생 스레드: threading.Thread로 분리, 수초 내 즉시 시작
④ 음원 재생 완료 → 통화 종료
⑤ 결과 수집 (MOS, 스크린샷 발신/수신 양방향)
```

#### 스크린샷 증적 요구사항

| 단계 | 발신자 화면 | 수신자 화면 |
|------|-----------|-----------|
| 통화 연결 직후 | ✅ 캡처 | ✅ 캡처 |
| 통화 종료 직후 | ✅ 캡처 | ✅ 캡처 |

### 2.2 TC_02 — 보이스피싱 감지 테스트

| 항목 | 내용 |
|------|------|
| **목적** | 보이스피싱 음원 발화 시 ixi-O 앱이 경고 팝업을 표시하고 사용자가 통화를 종료할 수 있는지 검증 |
| **사용 음원** | 설정에서 첨부한 **보이스피싱 통화 음원** (TC_02 할당 파일) |
| **PASS 조건** | 수신자 측에 보이스피싱 감지 팝업 표시 → 빨간색 통화종료 버튼 클릭 → 통화 종료 |
| **FAIL 조건** | 팝업 미표시 상태로 통화 종료 |
| **별도 구현 필요** | ✅ 전체 (기존 스크립트 사용 불가) |

#### 실행 시퀀스

```
① iOS ixi-O 앱에서 Android 번호로 발신  (또는 반대)
② Android ixi-O 앱에서 자동 수신
③ 보이스피싱 음원 재생 시작
④ [폴링] 수신자 화면에서 보이스피싱 감지 팝업 등장 여부 감시
   - 팝업 element ID / 텍스트 패턴 사전 정의 필요
   - 타임아웃: 음원 길이 + 30초
⑤ 팝업 표시되면:
   └─ 빨간색 통화종료 버튼 클릭 → 통화 종료 → PASS
      스크린샷: 팝업 화면 (수신자 측만)
⑥ 팝업 미표시로 통화 종료되면:
   └─ FAIL
      스크린샷: 통화 종료 화면 (수신자 측만)
```

#### 스크린샷 증적 요구사항

| 상황 | 수신자 화면 |
|------|-----------|
| 보이스피싱 감지 팝업 (PASS) | ✅ 캡처 |
| 통화 종료 화면 (FAIL) | ✅ 캡처 |

> **발신자 화면 캡처는 불필요** (수신자 측 감지 팝업이 KPI)

### 2.3 TC_03 — MOS 측정 테스트

| 항목 | 내용 |
|------|------|
| **목적** | 전용 음원으로 통화 품질 MOS 기준선(Baseline)을 측정. 네트워크/코덱 변경 전후 품질 비교에 활용 |
| **사용 음원** | 메인 화면에서 첨부한 **화자1/화자2 파일** 그대로 사용 (별도 TC 설정 불필요) |
| **PASS 조건** | ViSQOL MOS 측정 완료 + 보고서 생성 성공 |
| **FAIL 조건** | MOS 측정 실패 / 타임아웃 |
| **음단절 분석** | ❌ TC_03은 MOS 측정 전용 — 음단절 분석 포함 안 함 |
| **별도 구현 필요** | ❌ 기존 ViSQOL 파이프라인 재사용 |

> **음단절 분석은 TC_01/TC_02 실행 완료 후 자동으로 수행**된다. TC_03은 순수하게 MOS 기준선 측정만 담당한다.

#### 실행 시퀀스

```
① 기존 일반 통화 시나리오 실행 (TC_03 전용 음원 사용)
② iOS/Android 양방향 통화 녹음 수집
   (recordings/{runId}/ 저장)
③ 통화 종료 후 ViSQOL MOS 측정만 실행
   - ViSQOL v3 (iOS 발신 / Android 수신 양방향)
④ MOS 보고서 생성 (mos_report.html)
⑤ 대시보드에 MOS 점수 + 보고서 링크 표시
```

#### 대시보드 연동 표시 항목

- ViSQOL MOS (iOS → Android / Android → iOS)
- MOS 등급 배지 (우수 ≥4.0 / 양호 ≥3.5 / 보통 ≥3.0 / 불량 <3.0)
- "MOS 보고서 열기" 버튼 → HTML 보고서 브라우저 실행

## 3. 공통 요구사항

### 3.1 MOS 측정 및 음단절 자동 분석

| TC | MOS 측정 | 음단절 자동 분석 | 결과 표시 위치 |
|----|---------|----------------|---------------|
| TC_01 | ViSQOL v3 양방향 | ✅ 통화 종료 후 자동 실행 | 결과 카드에 통합 표시 |
| TC_02 | ViSQOL v3 (감지 이전 구간) | ✅ 통화 종료 후 자동 실행 | 결과 카드에 통합 표시 |
| TC_03 | ViSQOL v3 양방향 | ❌ MOS 전용 (음단절 없음) | MOS 전용 보고서 |

#### TC_01 / TC_02 음단절 자동 분석 흐름

```
TC_01 또는 TC_02 통화 종료
  └─ 통화 녹음 파일 수집 완료
       └─ [자동] analyze_hybrid.py 백그라운드 실행
            ├─ Gemini + librosa 음단절 분석
            ├─ ViSQOL MOS 측정
            └─ 결과를 해당 TC 결과 카드에 자동 첨부
                 ├─ 음단절 건수 + 심각도 배지
                 ├─ MOS 점수
                 └─ [📊 보고서] 아이콘 → HTML 보고서 열기
```

### 3.2 결과 데이터 스키마 (TcResult 확장)

```typescript
interface TcResult {
  // 기존
  runId: string;
  tcId: TcId;
  startedAt: string;
  finishedAt: string;
  durationMs: number;
  status: "PASS" | "FAIL" | "ERROR" | "RUNNING" | "SCHEDULED";

  // 신규 추가
  phase: number | null;            // TC_01: Phase 1/2
  mosIos: number | null;           // ViSQOL MOS (iOS → Android)
  mosAndroid: number | null;       // ViSQOL MOS (Android → iOS)
  // 음단절 분석 (TC_01 / TC_02 자동, TC_03은 null)
  dropoutCount: number | null;     // 음단절 건수 (TC_01/TC_02)
  severity: "없음" | "경미" | "보통" | "심각" | null; // TC_01/TC_02
  dropoutReportPath: string | null;  // 음단절 분석 HTML 보고서 (TC_01/TC_02)
  mosReportPath: string | null;      // MOS 보고서 (TC_03)
  screenshotPaths: string[];       // 캡처된 스크린샷 절대 경로 목록
  logLines: string[];
  errorMsg: string | null;
}
```

## 5. 반복 테스트 & 예약 테스트

### 5.1 반복 테스트 (Repeat)

| 항목 | 내용 |
|------|------|
| **반복 횟수** | 1 ~ 99회 설정 가능 (기본값: 3) |
| **반복 단위** | TC 단위 (TC_01 3회 후 TC_02 3회 등) 또는 세트 단위 (TC_01+02+03 × 3회) |
| **실패 시 동작** | 옵션: 중단 / 계속 / 크래시 시 재시도 |
| **대시보드 표시** | 진행 카운터 "2 / 5회" + 프로그레스바 |
| **결과 집계** | 반복 결과를 하나의 세션으로 묶어 PASS율 / FAIL율 / 평균 MOS 표시 |

#### 반복 옵션 UI 구성
```
[반복 실행]
  반복 횟수: [   3 ▲▼ ]
  반복 단위: ○ TC별 반복  ● 세트 반복
  실패 시:   ○ 즉시 중단  ● 계속 진행  ○ 크래시만 재시도
  [ ▶ 반복 시작 ]   [ 🛑 중단 ]
```

### 5.2 예약 테스트 (Scheduled)

| 항목 | 내용 |
|------|------|
| **예약 방식** | cron 표현식 또는 "X분 후 시작" 단순 딜레이 |
| **예약 조건** | 디바이스 연결 상태, Appium 실행 상태 사전 확인 |
| **대시보드 표시** | 예약된 TC는 `SCHEDULED` 상태 배지 + 카운트다운 |
| **취소** | 예약 취소 버튼 제공 |
| **알림** | 테스트 완료 시 macOS 시스템 알림 |

## 6. 대시보드 & 진행 상태 UI

### 6.1 TC 진행 상태 상태머신

```
IDLE
  │ 실행 버튼 클릭
  ▼
QUEUED (대기 중 — 선택한 복수 TC 중 차례 기다리는 경우)
  │ 실행 시작
  ▼
RUNNING
  ├─ Sub-status 스트리밍:
  │    "📱 앱 실행 중..."
  │    "📞 발신 중..."
  │    "🎵 음원 재생 중 (0:23 / 1:45)"
  │    "🔍 분석 중..."
  │
  ├─ PASS → 결과 카드 표시
  ├─ FAIL → 결과 카드 표시 (실패 원인 포함)
  └─ ERROR → 에러 카드 표시 (재시도 버튼)
```

### 6.3 실행 중 TC 상세 뷰 (클릭 시 확장)


## 7. 기술 검토 사항

### 7.1 TC_01 Phase 2: iOS 수신 시 음원 타이밍 동기화

**문제**: iOS 앱에서 수신 수락 시점을 정확히 감지하고, 통화 화면의 00:00 타이머와 음원 재생을 동기화해야 함

**구현 방안 (우선순위 순)**

| 방법 | 원리 | 장점 | 단점 |
|------|------|------|------|
| WDA + callTimer 폴링 | Appium으로 통화 타이머 element 감지 | 구현 간단 | ±500ms 오차 |
| CallKit 앱 내 이벤트 후킹 | iOS 앱에 WS 서버 삽입 → 수락 이벤트 push | 정밀도 높음 | 앱 빌드 수정 필요 |
| 오디오 세션 에너지 감시 | 오디오 입력 스트림 에너지 임계값 감지 | 앱 수정 불필요 | 통화 품질에 의존 |

**권장**: WDA 폴링 방식으로 PoC 후, 오차 허용 범위 벗어나면 CallKit 후킹으로 전환

```python
# 구현 예시 (tc01_runner.py Phase 2)
import threading, time

def wait_call_connected_ios(driver, timeout=30):
    """iOS 통화 타이머 00:00 감지"""
    start = time.time()
    while time.time() - start < timeout:
        try:
            timer = driver.find_element(By.ACCESSIBILITY_ID, "call duration")
            return True  # 타이머 등장 = 연결됨
        except NoSuchElementException:
            time.sleep(0.2)
    return False

def tc01_phase2(ios_driver, android_driver, audio_file):
    android_driver.make_call(IOS_NUMBER)
    if wait_call_connected_ios(ios_driver):
        # 백그라운드 스레드로 즉시 음원 재생
        t = threading.Thread(
            target=play_audio, args=(audio_file,), daemon=True
        )
        t.start()
        t.join()
    ios_driver.end_call()
```

### 7.2 TC_02: 보이스피싱 팝업 감지

- Appium `find_element` + `text` 패턴 매칭으로 팝업 감지
- 팝업 element ID / resource-id / accessibility label 사전 확보 필요 (앱 팀 협의)
- `WebDriverWait` + `expected_conditions.visibility_of_element_located` 사용
- 타임아웃 초과 시 → 스크린샷 + FAIL 처리

### 7.3 대시보드 ↔ Python 통신

현재 Tauri `invoke` + Python 서브프로세스 구조에서  
**실시간 진행 상태 스트리밍**을 위해 `tauri::Event`를 활용:

```
Python 스크립트
  └─ stdout에 구조화 로그 출력: "PROGRESS:tc01:phase2:0.45:음원 재생 중"

Rust (Tauri)
  └─ stdout 라인 파싱 → app.emit("tc-progress", payload) 이벤트 발생

React (프론트엔드)
  └─ listen("tc-progress", ...) → 실시간 상태 업데이트
```
