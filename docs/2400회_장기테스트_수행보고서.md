## 1. 개요

ixiO 통화품질 자동화 프로그램에서 **처음으로 시도한 대규모 장기 테스트**이다.  
12개의 예약 테스트(각 100세트 × TC_01·TC_02)를 순차 큐로 등록하고, 무인 자동 실행으로 약 4~5일간 연속 수행하는 계획이었다.

실제 수행 과정에서 **앱 중단, Race Condition, React StrictMode 이중 마운트, 상태 관리 결함** 등 다수의 문제가 발견되었으며, 이를 실시간으로 진단·수정하면서 테스트를 이어갔다.

이 보고서는 전체 수행 과정을 **시간 순서대로** 기록한다.

#### 11:04 KST — "이어하기" 팝업 미작동

**현상**: 앱 재시작 → #5가 즉시 `done` 처리됨. 재개 팝업이 뜨지 않음.

**근본 원인 — 두 useEffect의 Race Condition**:

```
렌더 사이클 (schedulesLoaded = true):
  ├─ [stale 복구 effect]
  │    → db_find_recent_session 비동기 호출 (Promise 비동기 대기)
  │
  └─ [schedules effect]  ← 동시 발동!
       → isAnyRunning=false → fireEntry(#6) 자동 실행
       → stale 복구 Promise 미완료 상태에서 큐 자동 실행
```

stale 복구 effect가 DB 조회를 비동기로 수행하는 동안, schedules effect가 자동 큐를 먼저 실행해 버림.

**수정 3건**:

1. **`staleCheckDone` 가드 state 추가**: stale 복구 완료 전까지 자동 큐 차단
2. **자동 큐 조건 강화**: `!isAnyRunning && staleCheckDone && resumePrompts.length === 0 && !hasStaleRunning`
3. **schedules effect deps 확장**: `[schedules, schedulesLoaded, staleCheckDone, resumePrompts]`

#### fireEntry 수정 1차 — `didFire` 패턴 (실패)

**시도**: `setSchedules` updater 안에서 `didFire = true` 플래그를 세우고, 바깥에서 `if (didFire) onTrigger()` 호출.

```typescript
let didFire = false;
setSchedules((prev) => { ...; didFire = true; return next; });
if (!didFire) return;  // ← 항상 false
onTriggerRef.current(...);
```

**실패 원인**: React 18에서 `setSchedules` updater는 **배치(batch) 처리**되어 즉시 실행되지 않음. `didFire`는 항상 `false`이므로 `onTrigger`가 호출되지 않음.

| Session ID | 시작 | 종료 | 결과 |
|-----------|------|------|------|
| `0f62db0f` | 19:28 | 19:44 | 1건 |

---

#### fireEntry 수정 2차 — `prev.some(running)` 가드 제거 (부분 성공)

**시도**: updater 안의 `prev.some(s => s.status === "running")` 가드를 제거하고, `onTrigger`를 무조건 호출.

**결과**: 테스트는 시작되었지만 칸반이 "대기중"에 머묾. DB에 세션이 생성되고 결과도 기록되지만, `schedules.json`에는 `sessionId`가 기록되지 않음.

| Session ID | 시작 | 종료 | 결과 | 비고 |
|-----------|------|------|------|------|
| `1a3090bb` | 19:44 | 23:56 | 1건 | 4시간 12분간 stuck 상태 유지 |

**근본 원인 식별**: `setSchedules` → `useEffect` → `saveSchedules` 경로의 effect 타이밍이 **비결정적(non-deterministic)**. `onTrigger` 호출 후 App 리렌더가 schedules effect보다 먼저 실행될 수 있음.

#### fireEntry 수정 3차 — `flushSync` (실패)

**시도**: `flushSync(() => setSchedules(next))` 로 DOM 커밋까지 동기 실행.

**실패 원인**: `flushSync`는 DOM 커밋을 동기화하지만 `useEffect`는 여전히 비동기. `saveSchedules()`가 제때 실행되지 않아 파일에 `sessionId`가 기록되지 않음.

#### fireEntry 수정 4차 — `schedulesRef` + 직접 저장 (성공, but…)

**수정**: effect-based 저장을 포기하고, **Ref에서 직접 읽기 → 즉시 파일 저장 → 상태 갱신** 패턴 도입.

```typescript
const schedulesRef = useRef<ScheduleEntry[]>([]);

function fireEntry(entry) {
  const prev = schedulesRef.current;           // Ref에서 최신 상태 읽기
  const next = prev.map(s =>
    s.id === entry.id ? { ...s, status: "running", sessionId } : s
  );
  schedulesRef.current = next;
  saveSchedules(next);      // 즉시 파일 저장 (effect 경유 안 함)
  setSchedules(next);       // React 상태 → UI 갱신
  onTriggerRef.current(...);
}
```

**동시에**: 모든 `setSchedules` updater 안의 `saveSchedules` 호출 **13곳 전부 제거**. schedules effect의 1곳 + `fireEntry`/`handleResume` 직접 호출만 유지.

**결과**: 파일 저장은 확정적으로 되었지만, **또 다시 칸반이 pending으로 되돌아가는 현상** 발생.

| Session ID | 시작 | 종료 | 결과 |
|-----------|------|------|------|
| `b204f465` | 00:21 (4/13) | 00:33 | 1건 |

**DB 교차 분석**에서 결정적 단서 발견:
- DB: `b204f465` 세션이 `started_at` 있음 + 결과 1건 기록 → 테스트가 실행됨
- schedules.json: 해당 `sessionId` 없음 → **`setSchedules`가 덮어씌워짐!**

#### 최종 수정 — React.StrictMode 이중 마운트 레이스 컨디션

**근본 원인**:

```
StrictMode mount effect 실행 흐름:
T0: 첫 mount → invoke("load_schedules") → Promise A 발생
T1: StrictMode cleanup
T2: 두번째 mount → invoke("load_schedules") → Promise B 발생
T3: Promise A resolve → setSchedules(parsed) → fireEntry → setSchedules(#6=running)
T4: Promise B resolve → setSchedules(parsed: #6=PENDING!) ← 덮어쓰기!
```

React `<StrictMode>`는 개발 모드에서 mount effect를 **2회 실행**한다. 두 번의 `load_schedules` IPC가 모두 비동기로 비행 중이며, Promise A가 resolve된 후 `fireEntry`로 `#6=running`으로 변경해도, 뒤이어 Promise B가 resolve되면 **원본 JSON(#6=pending)**으로 덮어쓴다.

**수정**: 표준 React ignore 패턴 적용:

```typescript
useEffect(() => {
  let ignore = false;
  invoke<string>("load_schedules")
    .then((json) => {
      if (ignore) return;  // StrictMode 1차 마운트 결과 무시
      setSchedules(JSON.parse(json));
    })
    .finally(() => { if (!ignore) setSchedulesLoaded(true); });
  return () => { ignore = true; };
}, []);
```

## 9. 교훈

### React 상태 관리

1. **`setSchedules` updater 안에서 Side Effect(IPC/파일 저장)를 절대 하지 말 것.**  
   React는 updater를 순수 함수로 가정하며, StrictMode에서 2회 호출, 배치 처리 등으로 실행 타이밍이 비결정적이다.

2. **Effect-based 저장은 "결과적 일관성"만 보장한다.**  
   `setSchedules` → `useEffect` → `saveSchedules` 경로는 중간에 다른 상태 변경이 끼어들 수 있다. 확정적 저장이 필요한 경우 **Ref + 직접 호출** 패턴을 사용해야 한다.

3. **StrictMode의 이중 마운트는 비동기 IPC와 반드시 충돌한다.**  
   Tauri `invoke`처럼 비동기 결과를 받아 `setState`하는 모든 mount effect에는 `let ignore = false` cleanup 패턴이 필수이다.

### 장기 테스트 운영

4. **"무인 자동 실행"은 모든 예외 경로를 커버해야 한다.**  
   앱 중단, 탭 이동, 큐 경합, stale 상태 등 단발 테스트에서는 드러나지 않는 문제가 장기 실행에서 표면화된다.

5. **디버깅 시 schedules.json 직접 조작은 위험하다.**  
   자동화 도구로 JSON을 조작할 때 전체 삭제 위험이 있으므로, Rust 커맨드를 통한 API 기반 조작이 안전하다.

6. **세션 데이터의 이중 기록 (DB + JSON)은 복구를 가능하게 했다.**  
   schedules.json이 전소되었을 때 DB `tc_sessions` 데이터로 복구할 수 있었다.
