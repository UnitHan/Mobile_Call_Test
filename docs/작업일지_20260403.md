## 6. TC_01~TC_04 플랫폼 하드코딩 버그 수정 (치명적)

### 문제
- TC 분리 시 각 TC 클래스가 **플랫폼을 하드코딩**하여 `_run_phases()` 구현
  - TC_01: `phase_call_from_android()` + `phase_answer_ios_sp2()` 고정
  - TC_02: `phase_call_from_ios()` + `phase_answer_android_sp2()` 고정
- 그러나 프론트엔드(`useTcRunner.ts`)가 TC_02/TC_04에서 **speaker를 자동 swap**하여 Python에 전달
  - 전역 설정: speaker1=iOS, speaker2=Android
  - TC_02 swap 후: speaker1=**Android**, speaker2=**iOS**
- TC_02 클래스가 `phase_call_from_ios()` 호출 → **Android 드라이버에 iOS 메서드 전송** → 전부 실패
- 원본 `run()` 메서드는 `self.speaker1_platform` 런타임 체크로 분기하여 이 문제 없었음

### 증상 (실제 테스트 로그)
```
📋 TC 모드: TC_02 → Tc02 클래스 사용
화자1: Galaxy S22 Ultra (SM-S908N)  ← Android인데
  플랫폼: Android
📱 speaker1: 익시오 앱 키패드 열기...  ← iOS 키패드 메서드 호출됨
  💡 수동으로 익시오 앱 키패드 탭을 열어주세요. (7초 대기)  ← 실패
📞 전화번호 입력 중 (iPhone): ...  ← iPhone 입력 로직으로 진입
```

### 수정
4개 TC 파일 모두 **원본 `run()`과 동일한 런타임 플랫폼 체크** 방식으로 변경:

```python
# 변경 전 (하드코딩 — 깨지는 코드)
self.phase_start_android_sp2_watcher()   # speaker2=Android 가정
result = self.phase_call_from_ios()       # speaker1=iOS 가정

# 변경 후 (플랫폼 자동 감지 — 원본과 동일)
if self.speaker2_platform == 'Android':
    self.phase_start_android_sp2_watcher()
if self.speaker1_platform == 'iOS':
    result = self.phase_call_from_ios()
else:
    result = self.phase_call_from_android()
```

### 변경 파일
| 파일 | 변경 내용 |
|------|-----------|
| `tc_01.py` | 발신·수신 phase를 `speaker1_platform`/`speaker2_platform` 런타임 분기 |
| `tc_02.py` | 동일 |
| `tc_03.py` | 동일 + vishing phase 유지 |
| `tc_04.py` | 동일 + vishing phase 유지 |

### 결과
- TC_01~TC_04 모두 **플랫폼에 독립적** → 프론트엔드 swap 여부에 관계없이 정상 동작
- 사실상 4개 TC 클래스의 `_run_phases()` 로직이 동일 (TC_01=TC_02, TC_03=TC_04)
- 차이는 vishing phase 유무뿐

## 반성할 점

### 1. TC 분리 시 "의미"를 코드에 박아놓은 실수
- TC_01="Android→iOS", TC_02="iOS→Android"라는 **시나리오 설명**을 그대로 코드 분기에 하드코딩
- 실제 런타임에서 speaker1/speaker2의 플랫폼은 **프론트엔드 swap에 의해 결정**되므로, TC 클래스가 플랫폼을 가정하면 안 됨
- 원본 `run()` 메서드가 `self.speaker1_platform`으로 런타임 분기하는 이유를 이해하지 못한 채 분리한 결과

### 2. "있는 그대로 분리"하지 않은 점
- 리팩토링의 기본 원칙: **먼저 동작을 보존한 채 구조만 변경** → 그 다음 최적화
- 원본 코드의 플랫폼 분기 로직을 TC 이름에 맞춰 "단순화"한 것은 동작 변경이었고, 이것이 버그의 직접적 원인
- 플랫폼 분기가 왜 있는지 충분히 이해하지 않고 제거한 점이 문제

### 3. 사이드 이펙트 반복 발생에 대한 근본 대응 부족
- 매 작업마다 사이드 이펙트가 발생하는 패턴이 반복됨
- 원인: 코드베이스의 여러 레이어(프론트엔드 swap → Rust 전달 → Python 플랫폼 감지)가 복잡하게 연결되어 있으나, 이 연결 관계를 문서화하거나 테스트로 검증하지 않음
- **speaker 할당 흐름** (useTcRunner.ts swap → Rust test_cmd.rs → Python IxioAutomatedTest.__init__)을 명확히 문서화하고, TC 분리 같은 구조 변경 전에 반드시 이 흐름을 확인해야 함

## 9. ADB 연결 끊김 시 자동 재연결 (android_call_handler.py)

### 문제
- RINGING 감지 → 수신 수락 과정에서 Wi-Fi ADB 연결 끊김
- `KEYCODE_CALL(5)` (rc=255) 이후 모든 ADB 명령이 `device not found` 실패
- iOS 발신단에서는 00:00 타이머 확인됨 (통화 자체는 연결됨) → 하지만 Android 측 OFFHOOK 확인 불가 → 통화 강제 종료

### 수정

#### `_accept_android_ringing_call()` — 전략 실행 루프
| 항목 | 내용 |
|------|------|
| `stderr`에 `"not found"` / `"cannot connect"` 감지 | ADB 재연결 시도 (최대 3회, disconnect → 1초 대기 → connect) |
| 재연결 성공 후 | OFFHOOK 즉시 확인 → 이전 전략으로 이미 수락된 경우 즉시 성공 반환 |
| 재연결 실패 | 다음 전략 계속 시도 |
| 재연결은 1회만 | `_adb_reconnected` 플래그로 중복 재연결 방지 |

#### `_start_android_answer_watcher()` — OFFHOOK 확인 루프
| 항목 | 내용 |
|------|------|
| OFFHOOK 미확인 + Wi-Fi UDID | 15초 폴링 **진입 전** `adb connect` 재연결 시도 |
| 재연결 후 300ms 대기 | 안정화 후 OFFHOOK 폴링 시작 |

### 대응 시나리오
```
② KEYCODE_CALL(5) → rc=255 (수락 성공, ADB 끊김)
```

## 10. 대본 기반 음단절 판정에 3-tier 품질 등급 도입

## 11. TC_02 독립 테스트 — ADB-only 발신 방식 전환

### 배경
- TC_02 (Android→iPhone) 독립 테스트 시 UiAutomator2 세션이 빈번하게 끊김
- Wi-Fi ADB(192.168.219.103:5555) 환경에서 UiAutomator2 세션 불안정 (33% 실패율)
- Appium 3.2.0 + uiautomator2 6.9.0 — 검증 안 된 3.x 메이저 버전

3. UiAutomator2 세션이 Wi-Fi 불안정으로 `instrumentation not running` 빈발
