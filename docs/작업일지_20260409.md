## 1. 예약 테스트 칸반 보드 버그 분석 및 수정

### 현상
- **100회 반복 테스트 1차** (어제 저녁 예약, 즉시 실행): 테스트는 새벽에 정상 완료됐으나 칸반이 [테스트 중] 컬럼에 멈춰있음
- **100회 반복 테스트 2차** (새벽 2시 예약): 예약 시각을 무시하고 1차 완료 직후 즉시 실행됨. 200건 테스트는 새벽에 모두 완료됐지만 칸반은 [대기중] 컬럼에 멈춰있음

### 근본 원인 — 조건부 렌더링으로 인한 컴포넌트 unmount

```tsx
// 문제 코드 (App.tsx)
{activeTab === "schedule" && <ScheduleTab ... />}
```

`ScheduleTab`이 다른 탭으로 이동하면 완전히 unmount(소멸)됨. 이로 인해 세 가지 버그가 연쇄 발생:

#### Bug 1 — `"테스트 중"` stuck

`isTcRunning` 변화를 감지하는 `useEffect` 내의 `prevRunningRef`가 unmount로 소멸 → 재마운트 시 `false`로 초기화. 새벽에 테스트가 완료돼 `isTcRunning`이 `false`가 됐을 때 컴포넌트가 없어 `"running" → "done"` 전환이 누락. 아침에 탭을 열어도 `prevRunningRef = false`, `isTcRunning = false` → 조건 `true && !false = false` → 전환 불가, 영구 stuck.

#### Bug 2-1 — 2AM 타이머 silent drop

탭을 이동하면 cleanup 함수가 `timerRefs` 내 모든 타이머를 취소:
```typescript
return () => { timerRefs.current.forEach((t) => clearTimeout(t)); };
```
2AM 타이머가 발화 전이면 여기서 취소됨. 설령 탭을 유지했더라도 발화 시각에 `isTcRunning=true`(1차 실행 중)이면 아무 처리 없이 타이머 종료.

#### Bug 2-2 — 재마운트 시 `isAnyRunning` 블로킹

아침에 탭 재방문 시 localStorage 상태: e1=`"running"` (stale), e2=`"pending"`.
```typescript
const isAnyRunning = schedules.some((s) => s.status === "running"); // → true (stale!)
if (!isAnyRunning && !isTcRunningRef.current) { ... }               // → 영구 블로킹
```
stale `"running"` entry 때문에 queueAutoStart가 실행되지 않아 e2가 [대기중]에 영구 stuck.

---

### 수정 내용

#### Fix 1 — `App.tsx`: ScheduleTab 항상 마운트 유지

```tsx
// 수정 전: 탭 이동 시 unmount
{activeTab === "schedule" && <div ...><ScheduleTab .../></div>}

// 수정 후: CSS display:none 으로 숨김 — 항상 마운트 유지
<div className="dashboard-container"
     style={{ display: activeTab === "schedule" ? undefined : "none" }}>
  <ScheduleTab .../>
</div>
```

→ 이것 하나로 Bug 1, Bug 2-1 원천 차단. 타이머가 살아있고 `isTcRunning` prop 변화도 계속 수신.

---

#### Fix 2 — `ScheduleTab.tsx`: 마운트 시 stale `"running"` 복구

앱 자체가 꺼졌다 켜진 경우(Fix 1로 커버되지 않는 케이스)를 위한 방어 로직 추가:

```typescript
// 마운트 1회만 실행
useEffect(() => {
  if (!isTcRunning) {
    setSchedules((prev) => {
      const hasStale = prev.some((s) => s.status === "running");
      if (!hasStale) return prev;
      const fixed = prev.map((s) =>
        s.status === "running" ? { ...s, status: "done" as const } : s
      );
      saveSchedules(fixed);
      return fixed;
    });
  }
}, []);
```

---

#### Fix 3 — `ScheduleTab.tsx`: `isAnyRunning` 판단 기준 수정

```typescript
// 수정 전: stale "running" entry 때문에 항상 true → 큐 영구 블로킹
const isAnyRunning = schedules.some((s) => s.status === "running");

// 수정 후: 실제 실행 중인지는 prop 기준(isTcRunningRef)으로 판단
const isAnyRunning = isTcRunningRef.current;
```

---

#### Fix 4 — `ScheduleTab.tsx`: 타이머 miss → 큐 편입 (silent drop 제거)

```typescript
// 수정 전: isTcRunning=true 이면 silent drop (타이머 영구 소멸)
const tid = setTimeout(() => {
  if (!isTcRunningRef.current) fireEntry(s);
}, ms);

// 수정 후: isTcRunning=true 이면 scheduledAt=null 변환 → 큐 편입
//  → 앞선 테스트 완료 직후 자동 실행되도록 보장
const tid = setTimeout(() => {
  if (!isTcRunningRef.current) {
    fireEntry(s);
  } else {
    setSchedules((prev) =>
      prev.map((e) => e.id === s.id ? { ...e, scheduledAt: null } : e)
    );
  }
}, ms);
```

| 상황 | 수정 전 | 수정 후 |
|------|---------|---------|
| 탭 이동 후 테스트 완료 | `"running"` stuck | `"done"` 으로 즉시 전환 |

## 2. DB 실시간 적재 버그 수정

### 문제 1 — tc_results 저장 시 FK 위반 (묵음 실패)

**원인**: `db_save_result`(결과 도출 즉시 호출) vs `db_save_session`(세션 완료 후 호출) 타이밍 역전  
→ `tc_results.session_id REFERENCES tc_sessions` FK 제약 위반 → `SqliteFailure code 787` 묵음 실패

**수정** (`src/hooks/useTcRunner.ts`):  
`sessionId` 생성 직후 `invoke("db_save_session", { finishedAt: null })` 선행 호출 추가.  
세션 완료 시 finishedAt 포함 재호출(upsert)로 기존 레코드 갱신.

```typescript
// 세션 시작 직후 DB 선행 등록 (FK 제약 통과를 위해)
invoke("db_save_session", {
  sessionId, tcIds, startedAt: sessionStartedAt,
  finishedAt: null, ...
}).catch(...);
```

### 문제 2 — React 상태 업데이터 내 invoke 비실행

**원인**: `invoke("db_save_result")`가 `setTcResults(updater)` 안에서 호출되고 있었음.  
React는 상태 업데이터를 순수 함수로 요구하며, 그 안의 비동기 side effect는 실행이 보장되지 않음.  
(개발 모드 StrictMode에서는 updater가 2회 호출됨)

**수정**:  
`invoke` 호출을 상태 업데이터 밖으로 분리.

```typescript
// 수정 전: setTcResults(updater) 안에서 invoke 호출 → 비실행
setTcResults((prev) => {
  ...
  invoke("db_save_result", { ... }); // ← side effect in updater (버그)
  return next;
});

// 수정 후: 상태 업데이트와 invoke 분리
setTcResults((prev) => { ...순수 상태 업데이트만... });
invoke("db_save_result", { ... }) // ← 밖에서 직접 호출
  .then(() => { /* logLines에 ✅ DB 적재 완료 추가 */ })
  .catch(...)
```

### 문제 3 — Tauri 커맨드 args 키 오류

`send_stats_email(payload: SendEmailPayload)` 형태의 커맨드를 프론트에서  
`invoke("send_stats_email", { fromAddr, ... })` 로 직접 전달 → `missing required key payload` 에러

**수정**: `{ payload: { fromAddr, ... } }` 형태로 래핑

```typescript
await invoke("send_stats_email", { payload: { fromAddr, appPassword, toAddrs, ... } });
```

### 적재 로그 실시간 표시

**수정** (`src-tauri/src/db_cmd.rs`):  
`db_save_result` 성공/실패 시 `test-log` 이벤트 emit 추가 → Python 로그 스트림과 같은 콘솔에 표시

```rust
.map(|_| {
    let msg = format!("[db] ✅ DB 적재 완료: {} ({})", tc_id, status);
    println!("{}", msg);
    let _ = app.emit("test-log", &msg);
})
.map_err(|e| {
    let msg = format!("[db] ❌ DB 적재 실패: {} — {}", tc_id, e);
    let _ = app.emit("test-log", &msg);
    e
})
```

## 6. 예약 테스트 데이터 영속성 강화 — localStorage → 파일 저장

### 문제
예약 목록(`schedules`)이 `localStorage`에 저장되고 있었음.  
Tauri에서 `localStorage` origin은 dev(`http://localhost:1420`)와 prod(`tauri://localhost`)가 달라,  
**코드 수정 후 재빌드 시 예약 목록이 전부 초기화(휘발)** 되는 구조적 문제.

강제종료(`kill -9`)·코드 수정·앱 업데이트 중 어느 상황에서도 예약 목록은 절대 삭제되면 안 됨.

### 수정 내용

**신규 파일**: `src-tauri/src/schedule_cmd.rs`  
DB와 동일한 앱 데이터 디렉터리(`~/Library/Application Support/com.qabulls.call/schedules.json`)에 저장:

```rust
// load_schedules: 파일 읽기, 없으면 "[]" 반환
#[tauri::command]
pub fn load_schedules() -> String { ... }

// save_schedules: JSON 문자열을 파일로 쓰기
#[tauri::command]
pub fn save_schedules(schedules: String) -> Result<(), String> { ... }
```

**`src-tauri/src/lib.rs`**:  
- `pub mod schedule_cmd` 등록
- `setup()` 내 `init_schedules_path(&data_dir)` 호출 (DB 초기화와 동일 경로)
- `invoke_handler`에 `load_schedules`, `save_schedules` 추가

**`src/components/ScheduleTab.tsx`**:

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| 저장소 | `localStorage` (origin 의존) | `schedules.json` 파일 (고정 경로) |
| 초기 로드 | `useState(loadSchedules)` — 동기 | `invoke("load_schedules")` — 비동기 |
| 저장 | `localStorage.setItem(...)` | `invoke("save_schedules", { schedules: ... })` |
| 가드 | 없음 | `schedulesLoaded` 플래그 — 로드 완료 전 빈 배열로 파일 덮어쓰기 방지 |
| stale 복구 | 마운트 즉시 실행 | `schedulesLoaded=true` 이후 실행 (로드 전 false positive 방지) |

```typescript
// 마운트 시 파일에서 비동기 로드
useEffect(() => {
  invoke<string>("load_schedules")
    .then((json) => { setSchedules(JSON.parse(json)); })
    .finally(() => setSchedulesLoaded(true));
}, []);

// schedules 이펙트: 로드 완료 전 저장 금지
useEffect(() => {
  if (!schedulesLoaded) return;
  saveSchedules(schedules);
  // ... 타이머 등록, 큐 자동 실행
}, [schedules, schedulesLoaded]);
```

### 보장되는 내구성

| 상황 | 수정 전 | 수정 후 |
|------|---------|---------|
| 코드 수정 후 `npm run tauri dev` 재실행 | 예약 목록 초기화 | 유지 |
| 강제종료 (`kill -9`) | 유지 (마지막 저장 시점까지) | 유지 |
| 앱 정상 종료 후 재실행 | dev/prod 빌드 간 공유 불가 | 항상 동일 경로에서 복원 |
| 앱 업데이트 (번들 재설치) | origin 전환으로 초기화 가능 | `app_data_dir()` 동일 경로 유지 |

## 7. iOS 재부팅 후 자동화 방안 검토

### 배경
테스트 중 아이폰을 재부팅해야 하는 시나리오에서 Xcode 빌드 설정 및 tunneld 연결을 자동으로 복구하는 방법 검토.

### 결론

| 상황 | 자동화 가능 여부 |
|------|----------------|
| 재부팅 후 **최초 passcode 입력 (BFU)** | **불가** — iOS 보안 정책, 소프트웨어 우회 없음 |
| 화면 잠금(슬립) 해제 | 가능 — XCUITest로 Springboard 조작 |
| tunneld 재시작 | 가능 — `launchctl kickstart` |
| 앱 재설치 | 가능 — `xcodebuild install --allowProvisioningUpdates` |
| 페어링 확인 | 가능 — `pymobiledevice3 lockdown pair` |

### XCUITest 잠금해제 한계

- **콜드 리부팅(BFU) 후**: `.xctrunner` 자체 실행이 iOS에 의해 거부됨 → 자동화 불가
- **슬립 상태 해제**: Springboard 조작으로 가능

```swift
XCUIApplication(bundleIdentifier: "com.apple.springboard")
  .otherElements["LockScreen"].swipeUp()
springboard.secureTextFields.firstMatch.typeText("123456")
```

### 실용적 자동화 흐름 (채택 권장)

**재부팅 트리거** → BFU 감지(lockdown 응답 없음) → ⚠️ 수동: passcode 1회 입력  
→ `launchctl kickstart tunneld` → `xcodebuild install` → 테스트 자동 재개

BFU passcode 입력 1회는 MDM 감독 기기에서도 우회 불가한 iOS 보안 설계 한계.  
현 자동화 구조에서는 재부팅 빈도를 최소화하고 이 1회 수동 입력을 허용하는 방향이 현실적 최선.
