## 1. 앱 재시작 시 "이어하기" 팝업 미작동 — Race Condition 수정

### 현상
- 앱 강제종료 후 재시작 시, 중단된 테스트(예약 테스트 #5, 60/100세트 완료)에 대해 "이어하기" 팝업이 뜨지 않음
- #5가 즉시 done 처리되고, 뒤의 #6이 자동 시작도 안 됨

### 근본 원인 — 두 useEffect의 Race Condition

```
렌더 사이클 (schedulesLoaded = true):
  ├─ [stale 복구 effect, deps: schedulesLoaded]
  │    → db_find_recent_session 비동기 호출 (Promise 비동기 대기)
  │
  └─ [schedules effect, deps: schedules, schedulesLoaded]  ← 동시 발동!
       → scheduledAt 과거 항목 변환 → setSchedules 연쇄
       → isAnyRunning=false → fireEntry(#6) 시도
       → stale 복구 Promise 미완료 상태에서 큐 자동 실행
```

stale 복구가 비동기 완료되기 전에 schedules effect가 자동 큐를 실행하여:
- 중단된 #5를 재개 대상으로 인식하지 못하고 done 처리
- 재개 팝업(`resumePrompts`)이 설정되기도 전에 #6이 발화됨

### 수정 내용

#### Fix 1 — `staleCheckDone` 가드 state 추가

```typescript
const [staleCheckDone, setStaleCheckDone] = useState(false);
```

- stale 복구 effect: 비동기 Promise.all 완료 후 `setStaleCheckDone(true)`
- stale 항목 없거나 이미 실행 중이면 즉시 `true`

#### Fix 2 — 자동 큐 실행 조건 강화

```typescript
// 수정 전
if (!isAnyRunning) { ... fireEntry(next) }

// 수정 후
const hasStaleRunning = schedules.some((s) => s.status === "running");
if (!isAnyRunning && staleCheckDone && resumePrompts.length === 0 && !hasStaleRunning) {
  ... fireEntry(next)
}
```

- `staleCheckDone` false → 큐 차단
- `resumePrompts` 미응답 → 큐 차단
- 기존 running 항목 존재 → 큐 차단

#### Fix 3 — schedules effect 의존성 배열 확장

```typescript
// 수정 전
}, [schedules, schedulesLoaded]);

// 수정 후
}, [schedules, schedulesLoaded, staleCheckDone, resumePrompts]);
```

## 2. "이어서 진행"/"처음부터 다시" 즉시 실행되지 않는 문제

### 현상
- 재개 팝업에서 "처음부터 다시" 선택 → pending 항목만 생성되고 테스트 미시작
- 대기열 앞(#6)이 먼저 실행됨

### 원인
`handleResume`/`handleResumeFromStart`가 새 항목을 `status: "pending"`으로 추가만 하고, 자동 큐가 대기열 순서대로 #6을 먼저 실행

### 수정 내용

두 핸들러를 수정하여 **즉시 running + onTrigger 호출**:

```typescript
function handleResume(prompt) {
  const sessionId = crypto.randomUUID();
  fireRef.current = true;
  const resumeEntry = { ...prompt.entry, id: `sch-${Date.now()}`, status: "running", sessionId, ... };
  // ref에서 직접 계산 → 즉시 파일 저장
  const prev = schedulesRef.current;
  const withDone = prev.map(s => s.id === prompt.entry.id ? {...s, status: "done"} : s);
  const next = [...withDone, resumeEntry];
  schedulesRef.current = next;
  saveSchedules(next);
  setSchedules(next);
  onTriggerRef.current(tcSet, ...);
}
```

`handleResumeFromStart`도 동일 패턴 적용.

## 3. fireEntry → 칸반이 "테스트 중"으로 안 넘어가는 문제 (근본 수정)

### 현상
- `fireEntry`로 테스트가 시작되지만, 칸반에서 #6이 "대기중"에 계속 남아있음
- DB에는 세션이 생성되어 실행 중이지만, schedules.json에 sessionId가 기록되지 않음

### 1차 시도: `didFire` 패턴 (실패)

```typescript
let didFire = false;
setSchedules((prev) => { ...; didFire = true; return next; });
if (!didFire) return;  // React 18 batched update로 항상 false → onTrigger 미호출
```

**실패 원인**: React 18에서 `setSchedules` updater는 즉시 실행되지 않고 배치됨. `didFire`는 항상 `false`.

### 2차 시도: `flushSync` (실패)

```typescript
flushSync(() => { setSchedules(next); });
```

**실패 원인**: `flushSync`는 DOM 커밋을 동기화하지만, `useEffect`는 여전히 비동기. schedules effect의 `saveSchedules`가 제때 실행되지 않음.

### 3차 시도: `schedulesRef` + 직접 저장 (성공)

**근본 원인**: `setSchedules` → useEffect → `saveSchedules` 경로에서 effect 타이밍이 React 배치 업데이트, StrictMode 등에 의해 non-deterministic. `onTrigger` 호출 후 App의 리렌더가 schedules effect보다 먼저 실행될 수 있음.

**수정**:

```typescript
// schedulesRef: schedules 상태를 항상 미러링하는 ref
const schedulesRef = useRef<ScheduleEntry[]>([]);

// schedules effect에서 동기화
useEffect(() => {
  schedulesRef.current = schedules;
  saveSchedules(schedules);
  ...
}, [schedules, ...]);

// fireEntry: ref에서 직접 읽어 즉시 저장
function fireEntry(entry) {
  if (isTcRunningRef.current || fireRef.current) return;
  fireRef.current = true;
  const sessionId = crypto.randomUUID();

  const prev = schedulesRef.current;           // ref에서 최신 상태 읽기
  const next = prev.map(s =>
    s.id === entry.id ? { ...s, status: "running", sessionId } : s
  );
  schedulesRef.current = next;
  saveSchedules(next);      // 즉시 파일 저장
  setSchedules(next);       // React 상태 동기화 → UI 갱신
  onTriggerRef.current(...);
}
```

→ effect 타이밍에 일절 의존하지 않음. 파일 저장이 확정적.

## 4. setSchedules updater 안의 saveSchedules 부작용 제거

### 현상
- StrictMode에서 updater가 2번 실행되어 `saveSchedules`(Tauri IPC)가 2번 호출
- 여러 updater에서 동시에 `saveSchedules`를 호출하면 IPC 경합 발생

### 수정
- 모든 `setSchedules` updater 안의 `saveSchedules` 호출 **전부 제거** (13곳)
- schedules effect의 `saveSchedules(schedules)` **1곳만** 유일한 파일 저장 지점으로 유지
- `fireEntry`/`handleResume`/`handleResumeFromStart`는 `schedulesRef` + 직접 `saveSchedules` 호출 (effect 경유 안 함)

## 5. React.StrictMode + 비동기 IPC 레이스 컨디션

### 현상
- `fireEntry`로 running 상태를 저장했는데, 직후에 pending으로 덮어씌워짐
- DB에 세션이 생성되었지만 schedules.json에는 sessionId가 없음

### 근본 원인

```
StrictMode mount effect 실행 흐름:
T0: 첫 mount → invoke("load_schedules") → Promise A 발생
T1: StrictMode cleanup (Promise A는 이미 비행 중)
T2: 두번째 mount → invoke("load_schedules") → Promise B 발생
T3: Promise A resolve → setSchedules(parsed), setSchedulesLoaded(true)
    → effects → 100ms 후 fireEntry → setSchedules(#6=running) → 테스트 시작!
T4: Promise B resolve → setSchedules(parsed: #6=PENDING!) ← 덮어쓰기!!!
```

### 수정

표준 React ignore 패턴 적용:

```typescript
useEffect(() => {
  let ignore = false;
  invoke<string>("load_schedules")
    .then((json) => {
      if (ignore) return;                     // StrictMode 1차 마운트 결과 무시
      try { setSchedules(JSON.parse(json)); }
      catch { setSchedules([]); }
    })
    .catch(() => {})
    .finally(() => { if (!ignore) setSchedulesLoaded(true); });
  return () => { ignore = true; };           // cleanup 시 플래그 세팅
}, []);
```
